# 协议要点

完整的消息格式以 `server/server.py` 的实现为准，这里是"读代码前先知道的几件事"。

## 连接

```
wss://<host>:8705            # 聊天（TLS，自签证书）
https://<host>:8443/chatapi/ # 账号与管理（nginx 反代到 8706）
```

连上后第一件事是登录：

```json
{"type": "login", "token": "<登录时拿到的 token>"}
```

服务端回 `{"type":"login_ok","uid":...}`，随后推送历史与名册。历史分批，客户端按 `ts` 稳定排序后再展示——**不要按到达顺序**，补历史会把旧消息追加到末尾。

登录态是**单端**的：`chat_users.py` 的 `new_session()` 会先 `DELETE FROM sessions WHERE uid=?`，
再写新 token。所以同一账号在新设备登录后，旧设备的 token 立即失效，
旧连接在下一次校验时被判为 gone 并断开——这是有意为之，不是 bug。

## 收发

```json
// 发送
{"type":"send","text":"...","q_ts":0,"q_text":"","q_from":""}
// 收到
{"type":"msg","uid":3,"name":"...","text":"...","ts":1700000000}
```

引用是可选的三个快照字段（`q_ts` / `q_text` / `q_from`），服务端原样存下来。**不要用消息 id 做引用**：撤回后 id 就没了。

## 撤回

```json
{"type":"recall","ts":1700000000,"uid":3}
```

服务端做两步：先把原消息从 `msgs` 里删掉（按 `ts` + 正文 + 发送者定位），
再插入一条 `sys=1` 的空正文系统消息，`ts` 用**当前时间**（`tip_ts`，不是原消息时间）；
广播出去的 `recall` 事件同时带原 `ts` 和 `tip_ts`，客户端据此删除本地那条、在原位置补一条
"某某撤回了一条消息"。

所以"位置保住"是客户端用 `tip_ts` 做出来的观感，服务端并不保留原 `ts`，原正文也不在了。

## 名册

```json
{"type":"roster","users":{"1":"YEHO"},"deleted":[7],"archived":[2]}
```

任何改名都会触发一次广播。客户端要把它当成"当前显示名的唯一来源"：历史消息里存的 `name` 只是发送时的快照，显示时优先查名册。

## 身份

- `uid` 不可变，只增不复用 —— 消息归属、名册、显示名全部按它解析
- `uuid` 用户可以自己改（30 天一次），**不能**当身份用
- `uid = 0` 表示老数据没带 uid（显示昵称快照）；`uid = -1` 表示账号已硬删
