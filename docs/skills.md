# 技能 `skills/`

给 AI 编码助手用的**行为准则**，不是能力扩展。三条都是"拦住在动手之前偷懒"的那种东西——
模型不缺工具，缺的是先想清楚再动手的纪律。

每个技能是一个目录，里面一个 `SKILL.md`：

```
skills/<name>/SKILL.md
---
name: <name>
description: <什么时候该用，写成触发条件而不是介绍>
---
正文
```

## 装法

DSH（DeepSeek Harness）自带 filesystem skill provider，会扫这几个目录：

| 位置 | 作用域 | 优先级 |
|---|---|---|
| `<项目>/.dsh/skills` | 当前项目 | 最高 |
| `<项目>/.agents/skills` | 当前项目 | 高 |
| `~/.dsh/skills` | 所有项目 | 中 |

**带文件监听**，拷进去立刻生效，不用重启、不用 reload。

```bash
mkdir -p ~/.dsh/skills
cp -r skills/* ~/.dsh/skills/
```

Claude Code 一类的实现读 `~/.claude/skills/`，文件格式（YAML frontmatter + Markdown 正文）一致，
正文里提到的工具名按你手上的实际工具改一下就能用。

## 三个技能

### `grill-me` —— 先问清，再拆步骤

用在需求含糊、要改多个文件、或者对方只丢来一句话的时候。

逼自己走四步：一句话复述 → 列出必须问清的空白（**最多 3 个，能自己查到的不要问**）→
拆成每步都带验收标准的步骤 → 把不可逆的步骤单独标出来先确认。

写不出验收标准，就说明这步还没想清楚。

### `tdd` —— 先让检查失败，再让它通过

用在写新代码、改已有逻辑、修 bug 的时候。

核心一句：**在写实现之前，先写出一个此刻会失败的检查。**
没红过的检查，你不知道它在测什么。

汇报必须给三样：检查是什么、改之前真的红过（贴失败输出）、改之后是绿的。

### `triage` —— 先定位，再动手

用在出问题、报错、行为没按预期的时候。

拿到原文证据 → 先复现 → 写**至少两个**假设、每个都配一个能证伪它的实验 → 二分收窄 →
区分现象和原因 → 找到根因才改 → 用同一套复现步骤验证。

只列一个假设然后去找支持它的证据，那叫确认偏误。

## 为什么是这三条

工具类技能（浏览器、文档、前端）解决"能不能做"；这三条解决"做之前有没有想清楚"。

实际踩过的例子：修一条消息管道，第一次归因为"限流配额"，第二次归因为"缓存没失效"，
两次都错——因为没做 `triage` 的那一步：拿到确切证据再下结论。第三次按流程走，五分钟定位到
真正的分支条件。
