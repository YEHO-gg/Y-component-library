# 先让检查失败，再让它通过

核心只有一句：**在写实现之前，先写出一个此刻会失败的检查。**
它逼你把"什么叫做完了"变成可执行的判断，而不是改完看着还行就交。

## 步骤

1. **找到验证手段**。按这个顺序找，别跳过：
   - 已有的测试（`npm test`、`pytest`、`go test`……）
   - 没有测试：写一个最小的断言脚本
   - 连脚本都不好写：一条能看出对错的命令，或改前/改后的截图对比

2. **先跑一次，确认现在是失败的**。
   这一步不能省。没红过的检查，你不知道它在测什么，也不知道它会不会永远绿。

3. **最小改动让它变绿**。只改能通过这一条检查的最少代码，别顺手重构。

4. **重跑全部检查**，确认没把别的地方搞坏。

5. **再清理**：去掉重复、命名改好。清理完**必须再跑一遍**。

## 脏活也要有验证

"这个不好测"是最常见的借口。退一步也要有：
- 命令行跑一遍，看退出码和输出
- 打日志，确认走到了哪一步
- 前后各存一份状态（文件内容、数据库行数、页面截图）做 diff

完全没有验证手段就开工，等于改完自己都没法判断对错。

## 汇报

必须包含三样：
1. 检查是什么（具体命令 / 文件）
2. 改之前真的红过（贴一行失败输出）
3. 改之后是绿的（贴一行通过输出）

只写"已修复""测试通过"不算——那是结论不是证据。
