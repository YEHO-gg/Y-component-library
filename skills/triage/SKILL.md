# 先定位，再动手

改代码之前先回答一个问题：**我确切知道是哪一行、哪个条件出的问题吗？**
答不上来就去查，别边猜边改——猜错的修改会叠成一团，最后连原始问题都看不清。

## 步骤

1. **拿到确切证据**：完整的报错文本、退出码、时间戳、日志行、截图。
   不要转述成"好像报了个 500"，要原文。

2. **复现**：能用一条命令、一个最小脚本重现它。复现不了就先解决"为什么复现不了"。

3. **写出至少两个假设**，每个都设计一个能**证伪**它的实验：
   ```
   假设 A：配置文件没被读到
     实验：打印实际生效的配置值 → 如果值变了，A 错
   假设 B：读到的是另一份文件
     实验：改一处、看行为跟不跟 → 跟就是 B 对
   ```
   只列一个假设然后去找支持它的证据，那叫确认偏误。

4. **二分**：每次排除一半范围。从最外层（调用方 / 入口）往里收，不要一开始就逐行读代码。

5. **区分现象和原因**。
   "日志里没有记录"是现象；"代码在这一步之前就 return 了"才是原因。

6. **找到原因再改**，改完用第 2 步的同一套复现步骤验证。

## 汇报格式

```
现象：……（原文证据）
假设：A / B
排除过程：A 被 X 证伪；B 被 Y 证实
根因：……（具体到文件:行 / 具体配置项）
改动：……
验证：同一复现步骤，现在的结果是……
```

## 常见翻车

- 先改一版"试试看" —— 试出来了也不知道为什么对，下次照样错
- 看到相似报错就套上次的结论 —— 同样的字面错误可以来自完全不同的原因
- 修完不重跑复现步骤 —— 修好了是你说的，验证过才是真的
