# 先问清，再拆步骤

这张单子的作用是拦住在"没搞清楚就开干"的那一步。需求里没写清的东西，不会因为动手快而消失，只会在后面变成返工。

## 什么时候必须用

- 对方一句话就交活了，但"做完"的标准没写
- 任务会改到多个文件，或者要跨好几个回合
- 有一步是不可逆的（删东西、改系统配置、发到外部、花钱）
- 你发现自己正在猜"他大概是想……"

## 步骤

1. **一句话复述**：用你自己的话说你要做什么。如果这句话你都写不顺，说明还没看懂。

2. **列出空白**（最多 3 个）：写下来必须问清才能动的地方。
   - 能自己查到的（读文件、看日志、看代码）**不要问**，先查。
   - 问的时候给出选项和你的倾向，别抛开放式问题。

3. **拆成步骤**，每步都带验收方式：
   ```
   1. 做 X  → 验收：命令/检查/肉眼看到什么，具体到能判断真假
   2. 做 Y  → 验收：……
   ```
   验收标准写不出来，就说明这步还没想清楚。

4. **标出危险步**：不可逆、花钱、碰对方数据的步骤单独标出来，动之前先确认一次。

5. **开工后按步骤走**。中途发现某步不成立，停下来说明，不要默默改路线——对方是按你给的步骤在跟你对话。

## 反面例子

- "我理解你的意思了，开始吧" —— 没复述就是没确认。
- 列了 10 个步骤但每个都没有验收方式 —— 那不是计划，是许愿。
- 问了一堆本可以自己 grep 一下就知道的事 —— 那也是偷懒。

## 收尾

汇报时先说结论，再对着步骤逐条说「做了什么 / 怎么验证的 / 实际结果」。没做成的步骤明确说没做成，不要糊过去。
